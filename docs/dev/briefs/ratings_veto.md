# P5 - Map-level team ratings and veto model (cs2bot.models.ratings, cs2bot.models.veto)

> Work-package brief: the requirements this package was built against. Keep it in sync when scope changes.

**Owned paths:** src/cs2bot/models/ratings.py, src/cs2bot/models/veto.py (helper modules allowed as src/cs2bot/models/ratings_*.py or veto_*.py), tests/models/ratings_veto/

**Tests:** tests/models/ratings_veto/

## Requirements

1. MapRatingModel (ratings.py): a Glicko-2 based rating system (Glickman, "Example of the Glicko-2 system": mu/phi/sigma on the Glicko-2 scale, g(phi), E, v, Delta, volatility update via the Illinois algorithm with system constant tau) adapted to CS2 maps:
   - Two levels: an overall team rating and a per-(team, map) rating. Effective map strength = shrinkage blend of the map rating and the overall rating, weight w = n_map / (n_map + k_shrink) (or an equivalent hierarchical formulation) - document and test the choice. A team's first game on a map starts from its overall rating with inflated phi.
   - Time: inflate phi between games according to elapsed rating periods (period length configurable, e.g. 7 days): phi_new = sqrt(phi^2 + sigma^2 * periods), capped at the initial phi.
   - Roster continuity: compare a team's lineup with its previous lineup (MapResultRecord.team1_lineup/team2_lineup); for each replaced player inflate phi (and optionally regress mu toward the population mean) - 1 change mild, 3+ changes close to a reset. Configurable.
   - Margin of victory: optional actual-score transform from the round score (e.g. win/loss blended with round share), default mild; a win must always give s > 0.5.
   - LAN adjustment parameter (default 0) and optional tier weighting.
   - API: RatingConfig (dataclass/pydantic with all knobs and defaults tuned on the synthetic universe); MapRatingModel(config: RatingConfig | None = None); fit(records: Iterable[MapResultRecord]) processes chronologically; update(record); predict(team1_id, team2_id, map_name, as_of: datetime, *, is_lan: bool = False, team1_lineup=(), team2_lineup=()) -> MapWinEstimate with p_team1_win and sigma (std of p from rating uncertainty: integrate the logistic over Delta ~ N(mu1 - mu2, phi1^2 + phi2^2) or use the delta method; components like {"overall": ..., "map": ...}); predict must use only games strictly before as_of (raise ValueError if asked to predict for a time before the last processed game, and provide fit_until(records, as_of) / a copy-able state so callers can fit up to a cut-off). rating(team_id, map_name | None, as_of) -> RatingSnapshot (mu, phi, sigma, n_games, last_played, plus display units r = 1500 + 173.7178 mu). Unknown team -> prior (p near 0.5, large sigma). map_advantage(team_id, opponent_id, map_name, as_of) -> float (logit units) for the veto model. save(path)/load(path) (JSON).
   - tune(records, grid: dict[str, list], *, holdout_fraction=0.25) -> tuple[RatingConfig, dict] minimising log-loss on a chronological holdout.
2. VetoModel (veto.py):
   - VETO_TEMPLATES for BO1 (6 alternating bans starting with the first-veto team, leftover played), BO3 (ban, ban, pick, pick, ban, ban, leftover decider), BO5 (ban, ban, pick, pick, pick, pick, leftover), BO2 (ban, ban, pick, pick, the rest not played) for a 7-map pool; handle pools of other sizes gracefully (generalise templates or fall back to bans until the right number of maps remains).
   - Learn each team's map preferences from VetoRecord history with recency weighting (half-life configurable, ~90 days) and Bayesian smoothing toward league-wide map pick/ban rates; an optional opponent-relative term using a map_advantage(team, opponent, map) callable (e.g. MapRatingModel.map_advantage) so a team bans maps where it is weaker than this opponent. Each veto step is a softmax over remaining maps with utility = a * preference(team, map, action) + b * advantage; fit a and b by maximum likelihood on historical steps (a simple optimiser is fine).
   - predict_sequences(team1_id, team2_id, fmt: MatchFormat, map_pool: list[str], *, first_veto: TeamSlot | None = TeamSlot.TEAM1, known_steps: Sequence[VetoStep] = (), top_k: int = 50, as_of: datetime | None = None, map_advantage=None) -> list[MapSequenceProbability]: exact enumeration (prune negligible branches) of veto paths, aggregated by the resulting played-map sequence + pickers; first_veto None -> 50/50 mixture of both orders; known_steps condition the remaining path (a complete known veto -> a single sequence with probability 1). Returned probabilities sum to ~1 (renormalise after top_k truncation and say so in the docstring). Also map_slot_distribution(sequences) -> dict[int, dict[str, float]] and p_map_played(sequences, map_name) -> float.
   - save/load.
3. Tests using the synthetic universe (true strengths and veto behaviour are known): Spearman correlation between fitted ratings and true strengths > 0.8; out-of-sample log-loss/Brier clearly better than the 0.5 baseline and reasonably calibrated (reliability bins); map-specific offsets help vs overall-only on a universe generated with large map offsets; roster change increases sigma; no look-ahead (as_of); unknown teams; save/load round trip. Veto: top-1 pick accuracy well above chance, probabilities sum to 1, templates per format, known partial and full vetoes, the first_veto None mixture.
